# Batch 16 — SX-015 Apple subscription notifications

Implemented locally on September 12, 2026. No deployment, App Store configuration change, live purchase/refund, or account mutation. SX-015 remains in progress.

`apple-store-notifications` verifies Apple's notification JWS with the official `@apple/app-store-server-library` 3.1.0. Three Apple root certificates are pinned in a source module with download URLs and SHA-256 fingerprints; incoming certificates cannot establish trust. Online certificate/revocation checks are enabled. Production verification requires the app's numeric Apple ID, bundle, and environment. Sandbox notifications require an explicit opt-in. A decoded environment hint only selects the verifier; it cannot bypass verification.

Verified subscription notifications fetch current subscription status from Apple's API. Both the returned transaction and renewal JWS are verified, and their product, original transaction, and environment must match. Active and billing-grace statuses grant coverage only until their expiry. Grace uses the signed renewal's grace-period expiry. Expired, billing-retry-without-grace, and revoked statuses do not grant access. A revoked transaction cannot override this through an otherwise active status response. Delayed notification types do not directly grant/revoke access.

The database records receipt UUID/hash and current status atomically. Completed duplicates avoid another API lookup. Known account bindings and account tokens must agree; unknown owners retain a status record without being assigned access. Lookup, signature, unsupported-notification, and database failures are not acknowledged. Test notifications record a receipt without querying subscription status. Raw JWS bodies and account tokens are not persisted in these receipt/status tables.

Mobile subscription verification now fetches and verifies the same current status, including grace, instead of relying solely on an individual historical transaction's expiry. Current metadata updates the same Apple status record through a trigger. Start times order mobile and push observations: an older in-flight request cannot undo a newer revocation. Other valid providers continue through the shared effective-premium lookup, AI decisions, and quota admission. Re-verifying a transaction also refreshes its stored status metadata.
