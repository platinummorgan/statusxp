# Batch 18 — SX-015 encrypted Google tokens and scheduled checks

Implemented locally on September 12, 2026. No deployment, encryption secret configuration, scheduler activation, live purchase, or provider/account mutation. SX-015 remains in progress.

Google mobile subscription verification and authenticated notifications now save an encrypted purchase token alongside the verified account binding. The new service-only RPC wrappers commit fulfillment or notification receipt/state, ciphertext, and the reconciliation job in one database transaction. A token-storage failure rolls back that transaction, allowing a retry. Consumables and Apple purchases retain their existing fulfillment path. Unknown-owner notifications retain current status without storing a token or assigning an account.

Tokens use Web Crypto AES-256-GCM with a fresh random 96-bit IV. Authenticated additional data binds ciphertext to its production/sandbox subscription identity. Decryption also checks the token's hash against that identity. The envelope contains only version, key ID, IV, and ciphertext; plaintext never enters these database RPCs, purchase metadata, or queue responses. The encryption key stays in Edge secrets, outside the database. This follows the [Web Crypto AES-GCM parameter requirements](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams).

`google_play_tokens` has RLS and denies client access. The service role can read ciphertext but writes only through the verified-flow wrappers. Internal save helpers are not directly executable by the service role. Saves require a matching live binding and lock the account against deletion. Binding removal or owner changes delete tokens and jobs; account deletion cascades while preserving the existing ownership tombstones. The wrappers preserve existing idempotency and observation ordering. Database-level envelope validation rejects extra fields, including accidentally supplied plaintext.

The scheduled endpoint now includes Google when both service-account and token-key configuration are present. It claims only jobs with ciphertext, a matching live binding, and a current provider-state row. It decrypts the token for the current-state API lookup, validates the returned environment/account, and applies the same atomic reconciliation as notifications. API, decryption, account, or persistence failures use the existing retry path without inventing a new entitlement state. Reconciliation re-encrypts with the active key, allowing gradual key rotation.

Superseded tokens are excluded from scheduling. Terminal expired/pending-canceled states with a known expiry older than 60 days are also excluded; unknown expiry remains retryable. Google documents that purchase tokens cannot be queried more than 60 days after expiration in its [subscription lifecycle guidance](https://developer.android.com/google/play/billing/lifecycle/subscriptions). Paused, held, and other potentially recoverable states continue to be checked. Provider errors do not by themselves establish terminal state.

Deployment prerequisites and activation:

1. Inspect live definitions and complete prerequisites through batch 17. Apply `supabase/migrations/20260912160000_google_token_reconciliation.sql` manually; do not use `supabase db push --linked`.
2. Configure Edge secret `GOOGLE_PLAY_TOKEN_KEYS` as a JSON object mapping key IDs to base64-encoded, cryptographically random 32-byte keys. Set `GOOGLE_PLAY_TOKEN_ACTIVE_KEY` to the key ID used for new encryption. Keep key material in the secret manager; do not commit it, put it in SQL, or use the Supabase service-role key as an encryption key. No real keys were generated or configured during this batch.
3. Deploy the updated purchase verifier, Google notification endpoint, and reconciliation endpoint with their shared modules. Configure keys before releasing the updated purchase/notification paths: known-owner Google subscriptions now fail closed if encryption configuration is absent. Existing Google service-account, Pub/Sub authentication, package, and ownership requirements still apply.
4. The worker continues to use batch 17's opt-in `ENTITLEMENT_RECONCILIATION_ENABLED=true`. The Edge flag `ENTITLEMENT_RECONCILIATION_SANDBOX=true` now includes both Apple and Google sandbox jobs. The existing six-hour success interval, bounded batches, leases, and retry backoff remain unchanged.
5. Monitor configured-provider coverage, missing-token binding counts, due-job age, failures, key IDs, and quota usage. Only keys already captured through the updated verified flows are schedulable. Historical hashes cannot recover plaintext tokens: restore/re-verification or a subsequent verified notification is needed. Previously acknowledged notification duplicates still skip lookup and do not backfill missing tokens.

Key rotation: add the new key to the key map while retaining old keys, then switch the active ID. Verified saves and successful scheduled checks rewrite ciphertext under the active key. Do not remove old keys until all retained ciphertext using them has been re-encrypted or intentionally removed. Superseded and long-expired tokens are not polled, so automatic rotation does not cover those records. Ciphertext currently remains until binding/account deletion; a separate terminal-record retention/rotation maintenance policy remains open. Keep recoverable secret backups separate from database backups.

Remaining SX-015 work: Stripe scheduling, terminal token retention/maintenance, consumable refund/action handling, legacy ownership/token cutover, and the full live lifecycle matrix. This batch reconciles Google subscription state; it does not acknowledge purchases, issue refunds, replay notification history, or change consumable credit policy.
