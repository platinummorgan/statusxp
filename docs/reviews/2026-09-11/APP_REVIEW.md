StatusXP app review — September 11, 2026

StatusXP's strongest opportunity is to become the dependable answer to three questions: “What have I achieved?”, “What should I play next?”, and “How do I compare with people like me?” The app already contains most of the features needed to deliver that experience. The next investment should improve trust, first-use clarity, and response times, followed by connecting the existing features into a compelling weekly habit.

This review covers the Flutter client, navigation and account flows, data repositories, Supabase functions and SQL history, Node sync workers, purchases, AI guides, community features, web delivery, native configuration, and validation infrastructure. The inventory contains 190 Dart files / 62,252 lines, 33 Edge Function directories, and 78 top-level SQL migrations. It uses working-tree code at commit `05faa51`, including existing uncommitted edits. Those edits were preserved. Findings come from source inspection, repository-wide searches, local validation, and browser inspection of public screens; this is not a claim that every runtime path or every line received independent verification.

Production database privileges, deployed functions, cron jobs, payment settings, and actual latency were not inspected. SQL findings therefore describe the checked-in definitions and require comparison with deployed state. This distinction matters here because the repository explicitly documents manual production SQL changes. No production writes, purchases, account linking, messages, or exploit attempts were made. Local browser checks blocked backend and analytics traffic and used no authenticated session. Authenticated screens were assessed from code and existing tests, not a live account. Android/iOS device performance and accessibility still need device testing.

The highest-priority security finding is the profile boundary. The baseline grants table access to `anon` and `authenticated`, and `profiles_select_policy` uses `true`. That table also contains platform authentication fields; current PSN linking writes access and refresh tokens directly to it. I found no corrective profile-read policy in the searched migration history, including the manual archive. The “Encrypted NPSSO” column comment is not evidence of encryption in the write path. Separately, `get-users` uses the service-role client to return five complete profile rows without a handler-level authorization check. A valid gateway JWT, if required, does not establish administrator privilege.

Move credentials into a private, server-accessible connection store; expose explicit public profile fields; limit profile edits to user-editable attributes. Check deployed grants before declaring an incident. If exposure is confirmed, revoke affected provider credentials and require reconnection. RLS restricts rows, not columns; broad table privileges need to be removed before selective column grants can be effective. [Supabase column security documentation](https://supabase.com/docs/guides/database/postgres/column-level-security).

Acceptance: anonymous visitors can read only intended public identity fields; users can edit only their own allowed profile fields; neither can read provider credentials, including through views or helper endpoints. Cover anonymous, owner, other-user, and service roles in database tests.

The premium compatibility migration reverses part of the earlier entitlement hardening. It grants authenticated users insert/update access to their own premium row and execution of `add_ai_pack_credits`. The latter is a `SECURITY DEFINER` function accepting caller-supplied user ID, credit quantity, and price without receipt verification. The current mobile client already uses `verify-store-purchase`, but the compatibility permissions remain in source. Its own comment says to remove them after the older-client rollout ends; current `pubspec.yaml` is 1.1.18+93.

Reconcile installed-version traffic, end this compatibility route, and retain fulfillment through verified server paths. Acceptance: a signed-in client cannot grant premium or credits by direct database calls; a verified transaction grants the intended entitlement exactly once; restoring another user's transaction fails.

Privileged maintenance code needs the same boundary. `force-stop-syncs` changes all running users' sync state using the service role without checking an administrator. The Node middleware explicitly allows requests if `SYNC_SERVICE_SECRET` is absent, including sync and admin routes. It also logs an unredacted received authorization header on rejection. Make production startup fail when required secrets are missing, use a shared administrative authorization helper, and remove or isolate obsolete deployed maintenance functions. Confirm which functions are actually deployed before treating source presence as live exposure.

The mobile guest homepage is a reproduced visual defect. `_GuestHome` uses a transparent `Scaffold`; the under-900px shell returns a `Stack` without the desktop's dark backing. At 390×844, white headline text disappears into a white page, and secondary text is effectively unreadable. The compact header also removes the explicit “Sign in” action and leaves “Join”. Give every responsive branch an explicit surface, use narrower padding and scalable headline sizes, and retain a clear returning-user route. Verify 390px, 768px, 899px, and 900px widths, plus enlarged text. Compare the [mobile capture](D:/Dev/statusxp/docs/reviews/2026-09-11/mobile-home.png) with the [desktop capture](D:/Dev/statusxp/docs/reviews/2026-09-11/desktop-home.png).

AI guide economics currently depend on cooperative clients. The screen consumes a credit separately, then calls a generation endpoint that neither verifies the user's identity in its handler nor checks/debits credits. Even with gateway JWT verification, a caller can bypass the UI's credit workflow. A provider error after the client debit can also charge for a failed guide. Put identity verification, bounded input, an atomic credit reservation, generation, and success/failure settlement behind one server workflow. Use a request ID so retries cannot double-charge. Apply appropriate server quotas to guide generation and related provider-backed endpoints. Gate sync frequency server-side as well: the inspected start functions check identity/current state but do not enforce the client's premium/cooldown rules.

Guide quality needs a separate improvement: the prompt requests current obtainability and missability, but generation has no source retrieval or verification. Add cited source material, platform/version context, “last checked” information, an explicit unknown state, spoiler controls, and reporting of incorrect advice. Reuse validated guide content by composite achievement ID and content version. These are product recommendations, not a claim that a particular generated guide was wrong.

Payment-event handling has several concrete failure modes. Stripe AI-pack fulfillment passes no event or checkout ID into the additive credit RPC. Re-delivery can therefore grant the same purchase again. Database errors are logged and the handler still returns HTTP 200, preventing normal delivery retries from repairing failed fulfillment. Subscription updates/deletions look up users by scanning the unpaginated first `listUsers()` response and matching email. They also update `is_premium` without limiting the operation to the Stripe entitlement, so a delayed Stripe deletion can revoke a newer entitlement from another source.

Persist unique provider event IDs and stable customer/subscription-to-user mappings; acknowledge only after durable acceptance; process fulfillment transactionally with a unique business key. Model entitlements per source and derive effective access. Stripe documents duplicate delivery and non-guaranteed event order, so both need explicit handling. [Stripe webhook documentation](https://docs.stripe.com/webhooks).

Twitch verifies a signature but does not retain processed message IDs or reject old signed timestamps in the inspected handler; `grantPremium` extends an existing expiry by another 33 days each time. Repeated messages can extend access repeatedly. Use durable message deduplication, freshness checks, and subscription-state reconciliation. [Twitch webhook guidance](https://dev.twitch.tv/docs/eventsub/handling-webhook-events/).

Mobile purchases have a better initial verification boundary, but lifecycle reconciliation needs verification. `isPremiumActive()` reads only `is_premium`, ignoring expiry. No Apple/Google renewal/refund notification handler was found among the Edge Functions. Existing production jobs may compensate, but that is unverified. Add a central expiry-aware entitlement calculation and verify renewal, refund, cancellation, grace period, restore, and account binding across stores. Acceptance for all providers: replay, reordered delivery, timeout-after-write, and database outage tests produce correct final access and credit totals.

Twitch authorization sends a constant `state` and the callback reads `code` without checking state. Generate a random, expiring state bound to the initiating session and validate it before code exchange. Reject missing, mismatched, expired, and reused values. Twitch explicitly recommends unique random state and rejecting mismatches. [Twitch OAuth documentation](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/).

Account changes also need more coherent client state. `currentUserIdProvider` reads mutable `authService.currentUser` but watches only the stable service provider. It does not watch `authStateProvider`; there is no explicit invalidation of that provider in the searched auth paths. The root `ProviderScope` persists. A guest-to-login or account-A-to-account-B transition can therefore retain a cached null/user ID and associated data. Derive the user ID from the auth stream with distinct-ID semantics and invalidate/dispose user-scoped state on identity changes. Test this without restarting the app, including returning to a previously opened public game page.

The PSN account merge implementation deserves a contained integrity repair. The helper uses legacy game/achievement identifiers, multiple independent writes, and often ignores returned database errors. The confirm endpoint accepts an old user ID and credential object from the request instead of a server-held, verified merge intent. RLS may reject cross-account writes; this review does not establish account takeover. It does establish that success reporting is not tied to an atomic, fully validated merge. Require proof of provider ownership, a short-lived server merge intent, compatible composite IDs, and transactional migration with checked results.

The catalog search race is straightforward: each keystroke updates `_searchQuery`, but `_loadGames` immediately returns while `_isLoading` is true. A request for an earlier query can finish and populate the list while the input displays a later query; the later query was never fetched. Platform/sort changes share this problem. Debounce input, assign a request generation/key, and accept results only for the active query. Reset pagination per query. Acceptance: with a delayed response, typing “elden ring” quickly must end with results for the full phrase, even if an earlier request completes later.

Sync workers already use batching and provider-specific recovery logic; the missing layer is durable orchestration. Express responds before work completes and runs jobs in process. Start functions use separate read/check/write operations, allowing concurrent starts to pass the same check. Restart recovery runs once, selects profiles older than a 15-minute cutoff, and has no durable lease claim. Recent interrupted jobs can be missed by that startup pass; multiple instances can compete for the same user. The client resume service helps only when a client returns.

Introduce a persistent `sync_jobs` lifecycle with atomic enqueue/claim, a unique active job per user/platform, lease expiry and heartbeat, persisted checkpoints, bounded global/provider concurrency, and retries with backoff. Pass a job ID to workers and load server-held credentials there. Use provider deltas and existing title checkpoints before considering more parallelism. Move optional artwork/story generation after core achievement ingestion so presentation work cannot delay fresh scores. Acceptance: kill a worker mid-sync, restart two workers, and demonstrate eventual completion with no duplicate active ownership and unchanged achievement totals on replay.

Leaderboard refresh reliability is especially relevant to the existing uncommitted trigger-removal migration. Its strategy—one refresh after a batch rather than one per achievement—is sensible. However, all three sync completion paths call `await supabase.rpc(...)` inside `try/catch` without inspecting the returned `error`. A PostgREST error result can be logged as successful completion. Check the response and persist failed refresh work for retry; make the score/cache version visible to clients. Preserve the existing optimization and verify its deployment instead of implementing another overlapping fix.

Analytics is the largest clear data-volume optimization. Timeline, rarity, trophy-type, and monthly activity methods page through raw achievements in batches of 1,000; several make separate passes over overlapping data, and recent trends make another pass. The top-level work is already started concurrently. Parallelizing it again will not eliminate transferred rows or database work. For a large account, request count scales with achievement history, even though charts need only counts and buckets.

Compute daily/monthly/platform/rarity summaries in SQL, return bounded series and totals, and reuse recent activity once. Consider incrementally maintained summaries when measurements justify them. Add deterministic ordering or cursor pagination where raw history is actually needed. The dashboard can likewise use one compact summary with a freshness timestamp instead of combining live StatusXP calculations with multiple cache/fallback reads. Several catch paths currently return zero or empty data; show last-known values with stale/unavailable state so service failures do not look like lost achievements.

Keep library search responsive at scale. The public catalog is already paginated; the personal grouped-games RPC loads the whole library, then Dart filters/sorts it. The desktop dashboard fetches the whole grouped library to display six games. Provide a bounded recent-games query and server filtering/pagination for large personal libraries, while retaining lightweight local filtering for already loaded rows. Validate 10-, 500-, and 5,000-game fixtures and a large achievement account with `EXPLAIN (ANALYZE, BUFFERS)` in staging. Index changes should follow actual plans, not guesswork.

Rendering and startup improvements should follow profiling. The roughly 2,974-line mobile dashboard calls top-level `setState` on every scroll tick, combining animation, network coordination, background selection, prompts, and card construction. It invalidates dashboard data both after the first frame and in `didChangeDependencies`. Isolate parallax with a narrowly scoped animation/listenable, split stable cards into widgets, and refresh data on meaningful events. Chart painters that always return `true` from `shouldRepaint` should compare their inputs. Respect reduced-motion settings and test representative midrange phones. Flutter recommends localizing rebuilds and profiling expensive effects. [Flutter performance guidance](https://docs.flutter.dev/perf/best-practices).

Startup awaits Firebase, Supabase/session work, and on mobile store initialization/restoration and reminder initialization before `runApp`. Render an app shell early, keep purchase-stream registration early enough to catch events, and defer optional analytics/product loading behind bounded initialization states. Consolidate the SDK's automatic token refresh and the app's custom refresh scheduling after validating resume behavior. Avoid clearing all browser storage for broad initialization failures; recover the specific invalid session while preserving unrelated preferences.

Web delivery has useful low-cost work. `vercel.json` forces `application/json` for every `/assets/(.*)` response, including images and fonts. Remove that blanket override and confirm actual MIME types. Pin Flutter in `build.sh` instead of cloning the moving stable branch. Audit why icon tree shaking is disabled; the local `main.dart.js` is 4,650,153 bytes before compression, which is a build-size observation, not a download-time measurement. Measure compressed transfer and cold-start performance before setting a bundle budget. Do not label the current JS release broken because the separate Wasm dry run warns.

The app's public HTML supplies one canonical URL and generic social metadata for all routes. Add HTML-rendered public profile/game previews and route-specific share images so a shared achievement is visible immediately outside the app. Keep Flutter for interactive signed-in functionality. Flutter's own web guidance distinguishes app-centric interfaces from document-centric, search-oriented content. [Flutter web FAQ](https://docs.flutter.dev/platform-integration/web/faq). The hardcoded 4.8/1,250 aggregate rating and “thousands” copy in `web/index.html` need substantiated provenance or removal; their accuracy was not verified.

Accessibility and community trust should be explicit acceptance work. Custom charts need readable text/table equivalents and meaningful semantics; test keyboard traversal, focus visibility, screen readers, enlarged text, contrast, and reduced motion. The fact that only one explicit `Semantics` wrapper appeared in the searched UI is not proof that all built-in controls lack accessibility. It does indicate that the custom visual portions deserve focused checks. Comment moderation runs before a client-side insert, while the SQL insert policy checks ownership only; direct inserts can bypass that workflow. Put moderation/publication state under server control, retain reporting/blocking tools, and verify ownership rules for co-op offers and acceptance.

Account deletion performs a long sequence of independent deletes and ends with auth deletion. Failures can leave partial state; storage objects and external billing cleanup are not addressed in that function. Make deletion resumable, coordinate it with active sync jobs, and verify database/storage/provider cleanup as separate tracked steps. Do not assume deleting an app account cancels a store subscription. Present the user's actual billing source and management route clearly.

For maintainability, consolidate the competing dashboard implementations, legacy V1/V2 repositories, duplicate avatar upload implementations, and old sync-service variants only after checking references. The V2-named dashboard repository still contains obsolete platform mappings but is not the provider's active implementation; that is a maintenance hazard, not proof that the live dashboard uses those mappings. The main dashboard, achievement screen, flex room, settings, and sign-in are large enough that extracting feature controllers and shared components will materially reduce review risk. Keep the existing feature-by-feature refactor scope rather than attempting a whole-app rewrite.

The release process is a major multiplier. The migration README directs developers to test SQL on production, conflicts with other state documentation, and warns that normal migration push can be unsafe. A later placeholder also records a remote migration without its schema changes. Recover the actual deployed schema and migration ledger, preserve history, establish a disposable staging reset, and move to forward-only reviewed changes. Do not follow the old README's suggestion to delete migration history as an automatic cleanup. Verify backup restore capability. The repository has no `.github` workflow directory; external CI may exist but was not verified. Add required analysis/tests/web-build gates, server tests, database authorization and migration checks, dependency scanning, and a small browser/device smoke suite. Existing tests cover useful presentation/domain behavior but do not exercise the payment-webhook and worker-restart failures above.

Observability should connect client symptoms to a server operation. Mobile Crashlytics exists; its wrapper intentionally returns on web. Add web error collection and structured, redacted server errors with sync-job/request IDs, provider, stage, retry count, and latency. Track incomplete refreshes, queue age, provider rate limits, and entitlement processing failures. Avoid recording raw Stripe event bodies, authorization headers, or account tokens. Build on the existing analytics events rather than replacing them.

These windows describe sequencing, not an estimate that one engineer can complete every item in twelve weeks. Split foundational changes into small deployable slices and move product experiments forward where they do not depend on unfinished security or data work.

Use a small operational/product scorecard. Proposed initial engineering targets are p95 warm dashboard data under one second, p95 bounded catalog queries under 500ms, and p95 analytics under two seconds for the agreed large-account fixture. Establish actual baselines first. Track p50/p95 first-sync duration separately by platform/library size; sync completion excluding required user reauthentication; cache freshness; duplicate grants (target zero); web/native crash-free sessions; and cost per completed sync/guide. Product metrics should include first-sync activation, week-one return, weekly users taking a meaningful progress action, premium feature activation after purchase, and referral-to-sync conversion. No uplift percentages or production speedups are claimed by this review.

My recommended first implementation batch is the privilege/credential fixes, repeat-safe payment acceptance, the mobile guest-page correction, and the search/auth-state defects. They protect the experience users already have while establishing a trustworthy base for the larger performance and growth improvements.
