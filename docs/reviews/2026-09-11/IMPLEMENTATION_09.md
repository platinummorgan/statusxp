# Batch 9 — Durable Stripe fulfillment

SX-013 is implemented locally. No Stripe objects, payments, live account state, functions, or production schema were changed during validation. Deployment and real Stripe test-mode lifecycle verification remain pending.

## Result

- Webhooks verify the signature over the original bounded payload (512,000 bytes maximum). The endpoint accepts POST only. Supabase JWT verification is explicitly disabled for this webhook in `config.toml`; Stripe signature verification remains mandatory inside the function.
- Each event ID is stored before processing, with a two-minute lease per subscription or checkout session. Checkout and subscription events for the same subscription share that lease. Concurrent delivery returns 503 while another delivery owns it; expired work can be reclaimed. A stale worker cannot commit after losing its lease.
- The handler fetches current Stripe state while holding the lease. It does not apply historical subscription snapshots in delivery order. This addresses Stripe's documented [lack of delivery ordering and possible duplicate events](https://docs.stripe.com/webhooks?locale=en-GB).
- A single PostgreSQL transaction records pack fulfillment, updates credits/purchase history, and marks the event complete. Unique checkout-session and payment-intent keys prevent two distinct events granting the same purchase twice. Database errors return 503, including ambiguous responses after a write; a retry observes the committed event and does not grant again.
- Only a paid checkout grants pack credits. `checkout.session.async_payment_succeeded` is supported, as described in [Stripe's fulfillment guidance](https://docs.stripe.com/checkout/fulfillment). Unpaid checkout completion is durably acknowledged without credits; a later paid event can fulfill it.
- Subscription status is stored separately for each Stripe subscription. Effective Stripe access requires `active` status and a future period end. A canceled subscription cannot revoke another active Stripe subscription. Stripe events also preserve an active non-Stripe entitlement, including Apple, Google, Twitch, or an active source-less entitlement.
- Customer ownership is stored by Stripe customer ID and Supabase user ID. Subscription rows reference that customer mapping. Checkout reuses the mapped customer, and new-customer creation uses a per-user Stripe idempotency key before binding it. Account deletion preserves a null-owner tombstone so the Stripe customer cannot be rebound to another account. Portal lookup uses this mapping, with no email search.
- AI checkout now accepts only a known pack type; client-supplied credits and price are ignored. The server catalog is small: 20 credits/$1.99, medium: 60/$4.99, large: 150/$9.99. SQL independently validates the paid USD amount and derives credits from that catalog. Subscription validation retains the existing single $4.99 USD monthly product. Raw webhook payload/email/error logging was removed from the affected fulfillment paths.

## Rollout and limitations

1. Reconcile existing Stripe customer IDs and subscription IDs against trusted server-created `user_id` metadata or original checkout `client_reference_id`. Do not bind by email. Backfill verified customer ownership through `bind_stripe_customer` before enabling the new checkout/portal flow. The mapping permits one Stripe customer per user; users with multiple historical customer records need explicit reconciliation before release.
2. Reconcile previous pack grants before replaying historical paid events into an empty fulfillment ledger. New event/session/payment-intent records prevent duplicates going forward; they cannot infer credits already granted by the old untracked webhook. Seed verified historical fulfillment records under a reviewed migration or restrict replay to the verified cutover boundary.
3. Inspect outstanding legacy one-time Checkout sessions: the previous code did not require a Stripe customer, so some paid sessions may have no customer ID. Those require verified manual reconciliation before cutover. The new handler returns 503 instead of inventing an email-based owner or silently acknowledging an unfulfilled purchase. Unknown legacy prices and missing owner metadata likewise require reconciliation.
4. Apply `20260911200000_stripe_fulfillment.sql` manually using the repository migration procedure. Do not run `supabase db push --linked`. Deploy all four Stripe functions together with the webhook's signature-based authentication configuration. Existing client request shapes remain compatible; no Flutter change is needed in this batch.
5. Subscribe to checkout completion/async payment success and subscription created/updated/deleted events. Confirm webhook configuration is compatible with the pinned Stripe API version `2023-10-16`; the code retrieves current objects with that version. Exercise controlled Stripe test-mode purchases, duplicate delivery, reordering, cancellation, DB interruption, and portal access before live release.
6. Monitor `stripe_webhook_events` with `state='pending'`, expired leases, and Stripe failed deliveries. Stripe retries are the delivery worker in this implementation: no 2xx is returned until fulfillment or an intentional ignore is committed. If retries are exhausted, investigate the pending event and resend it through Stripe after correcting the cause. Do not delete completed event or fulfillment records to retry an operation.

Provider requests have a 20-second timeout and one SDK retry; failed processing leaves the lease to expire. This trades some retry latency for safe ownership. There is no independent queue poller or claimed end-to-end live payment test. No event payloads/customer emails are stored in the new ledger, but event/customer/payment/subscription ID tombstones are retained for replay protection.

Refunds, disputes, grace-period policy, and full cross-provider fallback/expiry projection remain part of SX-015. A Stripe subscription is retained when another source is active, but activation after that other source expires still needs the unified lifecycle work. This batch does not automatically migrate historical accounts or infer historical purchases.
